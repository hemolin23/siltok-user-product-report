# Siltok 用户运营与产品技术汇报

> 汇报日期：2026-09-23  
> 面向：产品与技术团队

## 一、结论先行

本阶段已经完成从用户发现、微信建联、筛选、签约、设备分配、测试组织到反馈归档的完整用户运营链路。当前问题已经不再是“找不到精准用户”，而是精准用户在价值理解、协议、排期、测试执行和产品成熟度上持续流失。

## 用户从加入到付费的五个问题

这是一条待验证的转化路径，不是已跑通的付费漏斗。现有事实只支持“有用户愿意了解和测试”；留存、核心用户与付费均缺少可信基线。

特别需要区分“愿意配合”和“认可产品”。目前配合度高的参与者中，部分首先对技术探索、模型开发和新工具感兴趣，愿意投入时间协助共创。这是珍贵的早期信号，却不能证明产品已经足够好用。用户付出的时间、测试成本与真实反馈，尚未稳定换回可交付结果，交换价值仍远未充分成立。

**价值交换是增长的前置条件。**用户愿意投入时间、测试与学习成本，交出真实工作流、反馈和案例，最终才可能付费；公司相应必须提供低门槛、稳定远程连接、足够算力与设备、相对云 / API 的成本或效率优势、能跑通的工作流、技术支持、迭代响应和核心用户权益。只有交换成立，才可能依次从 Beta 走向深度共创、留存、付费、案例与推荐。这是待验证的路径，不是已达成的成果。当前计划若从“有产品”直接跳到 100 / 300 个用户与销售增长，就遗漏了价值交换这一关键验证；应先在窄场景中证明用户投入能够换来可交付收益。

1. **为什么加入？** 用户首先看自己的问题能否被解决。内测申请里已有成本、批量生产、动态一致性等明确诉求；对于短剧与电商用户，还要展示质量与交付场景。用具体任务和可见样例解释价值，比介绍“端侧 AI”更有效。衡量是否能从建联走到明确任务和首次预约。
2. **加入之后得到什么？** 用户应得到一条低摩擦的首次体验路径：任务卡、适用模型、设备时间、操作指引、可带走的输出与原工作流对照。当前先签约、排设备、学操作的成本偏高，而失败输出会进一步抵消收益。衡量从预约到首个可用结果的时间与完成率。
3. **为什么持续测试？** 用户需要看到问题被处理、结果持续改善，且不必每次重建参数、素材和任务。现有模糊、错字、音频回声、断连、模型不可用等反馈必须关联任务 ID 与版本并复测。衡量二次提交、回访任务及反馈闭环率。
4. **为什么成为核心用户？** 产品必须进入真实生产流程：资产和工作流可复用，质量可验收，批量与团队协作可成立，专业反馈能影响优先级。仅有更多模型或更长 Beta 期不足以产生核心用户。衡量真实项目使用、每周重复任务、资产复用与主动共创。
5. **为什么付钱？** 用户需看到相较现有云服务或人工流程可量化的净收益：每条可交付内容的总成本、总耗时、稳定性、隐私与可控性。云端公测中“更快但画质下降和断连”说明单次推理速度不能替代交付价值。应以真实项目做小额付费试点，验证价格接受度、复购和单位交付成本；目前没有已核验的付费转化数据。

### LibTV 产品设计对照：只吸收可验证的方法

从用户提供的多篇 LibTV 拆解中，最值得纳入当前汇报的是三条产品设计启发：一是从单镜头生成转向完整项目，把剧本、分镜、角色资产、输入、输出与版本关联起来，让局部返工可定位、可重做；二是 Agent 快速搭骨架与人工逐镜头精修并存，两种入口共用同一可回溯项目；三是让用户在操作前看清能完成什么、要花多少时间与成本、能拿到什么结果。官方[网站](https://www.liblib.tv/)展示项目、资产、Agent 等入口，[Agent Skill 仓库](https://github.com/libtv-labs/libtv-skills)提供公开的调用方式。

这些是设计参照，不是 Siltok 已具备的能力。材料中关于 LibTV 收入、客户数、优惠、模型效果及其他竞品优劣的说法未在本次独立核验，故不用于汇报结论。团队席位、积分池和复杂导演台可留作后续竞品研究，不应越过当前连接稳定、可用输出与工作流闭环的优先级。

本地文件中可复核的公开联系方式下限为 **693 个**；各渠道通过数按现有口径合计 **238 人次**，但尚未进行跨渠道去重。愿意测试者共 **18 人**，其中 **11 人已签协议、3 人未签、4 人为内部免签**。外部测试者协议完成率为 **78.6%**，说明签约不是最大漏斗，真正的流失发生在“加微信后愿不愿意投入测试”。

产品侧最重要的判断是：用户需要的不是一台“端侧 AI 设备”，而是一套能够稳定产出可交付结果的 AI 生产基础设施，包括工作流、模型、任务队列、资产、API、恢复机制和真实输出标准。端侧只在高频、成本敏感、隐私、可控和可复用场景下有明显价值；对团队用户，云算力、API 和队列比共享单机更重要。

### 4. 为什么精准用户仍然大量不转化

1. **认知不成立**：用户不理解端侧 AI，无法快速将其映射为自己的成本、质量或效率收益。
2. **切换动机不足**：云服务已经够用，低频用户没有迁移本地的必要。
3. **信任与协议摩擦**：加微信后很快进入身份核验、NDA 和合作协议，决策成本陡增。
4. **执行成本过高**：排设备、约时间、学习、跑任务和写反馈都要求用户投入时间。
5. **需求时点不匹配**：身份精准不等于用户此刻正在采购或更换工具。
6. **首次价值太晚**：沟通步骤多，但用户没有在前 15–30 分钟内获得一个看得见的结果。
7. **已读不回是综合结果**：信息过长、价值不明确、没有强痛点、工作繁忙、对陌生测试缺乏信任都会表现为已读不回。

## 三、用户案例反馈：分类、质量、Bug 与建议

### A 级反馈：可用于产品或研发决策

#### 1. 云端 5090 与本地 4060 对比

- 同模型、同提示词下，云端 5090 生成 5 秒视频约 10 分钟，本地 4060 约 50 分钟，速度约提升 5 倍。
- 但云端结果质量更差，选择 1080P 时观感接近 480P。
- 本地可以得到较好的光影和雾效，云端同任务无法复现。
- 批量或长任务有频繁断连。
- 非加速任务超过 1 小时仍模糊，说明质量问题不能只归因于加速。

判断：问题指向模型版本、推理或渲染链路、输出规格标注和任务持久化，而不只是算力。

#### 2. 电商与短剧团队访谈

- 电商团队需要飞书数据源、验证过的脚本、人物和商品替换、官方 API 与批量生成。
- 短剧团队质量优先，当前 H3 质量与商业交付仍有差距。
- 5070 的生成时间波动大，最长约 2467 秒；5090 相对稳定。
- 单台端侧设备约支持 3 个并发用户，10 人团队会出现明显排队。

判断：团队场景优先需要官方 API、云算力、队列与批量生产能力，不应优先堆叠复杂节点画布。

#### 3. 倪海敬（独立创作者 / ComfyUI）

- 图像工作流基本可用，但存在披风遗漏、画面模糊、武器重复和元素数量错误。
- 文生视频模糊、人脸崩坏；图生视频相对可用。
- 提供了分阶段提示词和“插值扩展 sigma”节点参数建议，具备可操作性。

### B 级反馈：有价值但复现条件不足

#### 杨伟科（海外艺术家 IP / App 电商广告）

- 动作战斗图出现握手与刀柄分离。
- 世界观图混入无关中文文字。
- 封面元素融合不足；图生图鞋色漂移。
- 视频任务 1–2 模糊不可用，3–4 较好。
- 小号中文文字模糊、错字和不规范。

#### 耿顺洋（动漫 / 漫剧 / 互动内容）

- 部分图像模型不可用，点击生成后才告知。
- AI 对话响应慢。
- 非全量模型下，15 秒 720P 视频约 60 分钟。
- 成片音频不清晰并有回声。

### 问题分类

| 类别 | 代表问题 | 建议优先级 |
|---|---|---|
| Bug / 稳定性 | 断连、任务失败、模型不可用后置提示、长任务无法恢复 | P0 |
| 输出质量 | 人脸模糊、肢体结构、颜色漂移、小字错误、音频回声、1080P 名不副实 | P0 |
| 性能 / 容量 | 5070 长尾、15 秒 720P 约 60 分钟、单机并发低 | P1 |
| 产品功能 | API、队列、进度通知、资产库、项目管理、参考图角色、自动拼接 | P1 |
| 专业能力 | 自定义模型、LoRA、ComfyUI 工作流、简单/专业模式 | P1/P2 |

### 为什么高质量反馈少

- 多数用户没有走到真实任务阶段。
- 复现、截图、记录参数和写建议的成本过高。
- 断连、排队和环境摩擦过早暴露，使反馈停留在“能不能跑”。
- 表单、聊天、会议、共享文档和测试表缺少统一任务 ID。
- 自由探索任务过宽，容易产生描述性意见，难以形成可验收的问题。

反馈进入研发至少要包含：可追溯来源、业务影响、复现条件和验收标准。

## 四、对产品和现状的观点判断

1. 产品应该被定义为 AI 生产基础设施，而不是端侧硬件。
2. 端侧和云端不是二选一，应按用户任务分工：端侧负责高频、隐私、可控与稳定复用；云端负责弹性算力、团队并发和低频需求。
3. 速度不能掩盖质量与稳定性。更快地产出不可用结果并不产生商业价值。
4. 用户运营正在承担产品教育和人工调度系统；如果产品不降低这些摩擦，运营规模越大，人工负担越重。
5. 下一阶段不宜继续只扩大线索池，应优先完成 3 个真实案例闭环。

## 五、功能性和性能的区别

- **功能性**：产品有没有某项能力，例如文生视频、图生视频、API、资产管理、工作流导入。
- **质量**：结果是否能用于真实交付，例如人脸、动作、文字、声音、清晰度和提示词遵循。
- **性能**：一次任务多久完成，包括冷启动、P50、P90、吞吐和单位视频时长的生成时间。
- **稳定性**：任务能否持续完成，包括失败率、断线恢复、重试和任务持久化。
- **容量**：系统能同时服务多少人，排队多久，资源如何调度。
- **可用性**：用户是否理解和会使用，包括能力说明、参数保留、错误提示和简单/专业模式。

真正的商业指标不是“生成一次多少秒”，而是：

**一个可用镜头的总时间 = 排队 + 生成 + 失败重试 + 抽卡次数 + 人工筛选与返工。**

## 七、建议会议确认和未来两周动作

### 会议确认

1. 一个首发方案：目标用户、三项任务、端云分工和价值承诺。
2. 一套验收标准：质量、速度、稳定性、容量和真实输出规格。
3. 一个闭环台账：用户—协议—设备—任务—反馈—复测全部关联。

### 两周优先动作

1. P0：修复断连、任务丢失和输出规格不一致，建立任务 ID 与日志。
2. P0：选 3 位真实用户跑相同的窄任务，记录首次可用率与总耗时。
3. P1：将 18 位测试者统一录入状态台账。
4. P1：把首次体验改成 15–30 分钟可获得结果的轻量任务。
5. P1：明确官方 API、队列和云算力是否进入近期路线图。

## 九、专业 CG 导演新增反馈

这组反馈由用户在 9 月 23 日补充，目前是定性的专家观察。待原片、对照版本和生成参数关联后，可升级为可复测的质量案例。

| 内容 | 被认可的表现 | 不足 | 建议对照方式 |
|---|---|---|---|
| 海外短剧 10 秒视频 | 景深较好；人物微表情自然，眨眼尤其明显 | AI 感重、影调不足、视听语言单一 | 与自己制作的影调版本并排比较光比、色彩层次、镜头调度和情绪表达 |
| 游戏视频 | 暂无明确可交付优势 | 没有达到预期；动作缺少动画规律；人物手指崩坏 | 与已有分镜逐镜比较动作起承转合、关键姿态、连续性和手部结构 |

这说明专业用户评价视频时不只看“清晰”和“生成成功”，还会按摄影、表演、动作设计和分镜语言判断是否可用于项目。技术侧应保留原片、参考分镜、提示词、模型、种子和输出版本，才能把主观意见转成测试任务。

## 十一、新人接手的操作步骤

1. **准备候选名单。** 在 [建联工作台](https://siltok-signal.qingyu-lu-ai.chatgpt.site)查看账号内容和原始作品，记录平台、稳定 ID、创作方向、公开联系方式与来源链接，同一微信号只保留一条主记录。完成后应能说清为什么找这个人。
2. **写首条消息。** 只说明身份、对方的具体作品和一个相关问题。记录“已申请、已通过、已回复、待跟进、无意向”。不要在首条塞进产品介绍、协议和长问卷。参考[建联沟通任务](codex://threads/01a0ad2a-a406-7601-b521-a82667c2eb71)。
3. **确认真实任务。** 问对方现在用什么工具、最近做过什么、最卡哪一步，以及能否投入 15–30 分钟。有明确任务再推进体验；云端已满足需求的人保留联系即可。
4. **安排体验。** 明确适用协议、设备空档、3 天内的自由测试方式、最小任务和负责人。把下载安装、连接和求助的[快速上手指南](https://hemolin23.github.io/siltok-quickstart-guide/)发给用户。台账记录预约时间与状态。
5. **执行任务卡。** 保存用户原方案和输入，固定模型、参数、分辨率、时长与成功标准；记录任务 ID、排队、执行、失败重试和输出。导演类测试额外保留参考分镜与影调对照。
6. **收集反馈。** 先问哪里不能交付、哪一步费时，再问意外做得好的地方。原话、运营归纳和研发判断分开写；Bug 补日志与复现条件，质量问题补原片与对照。
7. **复测和汇报。** 让原用户用同一素材复测，比较首次可用率、可用镜头总耗时和继续使用行为。每个案例以“原问题—采取动作—得到结果—下一步决定”收口。

特别注意：通过微信、愿意测试、签协议、完成测试、愿意继续使用是五个不同状态，不应混写为同一个转化指标。
